# 물류 로봇 데모 — 시뮬레이션

기획서 `물류로봇데모_기획서 2.pdf`의 셀을 ROS 2 Jazzy + Gazebo Harmonic으로
그대로 옮긴 것이다. 확정 제원, 도달 검증 수치, 적재 격자 공식, 카메라 배치,
상태 기계, MES 스키마가 전부 기획서에서 왔다.

로봇은 **FAIRINO FR5**(v6, `fr5c`나 `fr5l`이 아닌 기본 FR5), 툴은 **ES45 진공
그리퍼**. 카메라는 넷이다.

| ID | 위치 | 기종 | 역할 |
|----|------|------|------|
| C1 | 컨베이어 탑뷰 | **D435f** | 판독 전담. 이 한 대로 판독이 끝난다 |
| C2 | 팔레트 탑뷰 | **D455** | 적재 확인, 디팔레타이징 전 재확인, 적층 붕괴 감지 |
| C3 | 갠트리 기둥 중단 | 미정 | MES 기록 사진, 트윈/관람 화면 |
| C4 | 손목 그리퍼 위 | **D405** | 판독 실패 시 근접 재시도 |

C3는 기획서에도 기종이 비어 있고 지시에도 없어서 일반 RGB로 두었다.
`cell.yaml`의 `cameras.c3_scene.model` 한 줄만 바꾸면 확정 기종으로 갈린다.

## 지금 바로 확인할 수 있는 것

ROS도 Gazebo도 없이, 이 저장소만으로 돌아가는 검증이 셋 있다. 배치가 맞는지,
팔이 실제로 닿는지, QR이 정말 읽히는지를 시뮬레이터를 켜기 전에 답한다.

```bash
python3 tools/verify_layout.py
```

기획서 "배치와 도달 검증"의 수치를 `cell.yaml`에서 다시 만들어 낸다.
로봇 중심에서 판독 위치 **414**, 팔레트 1 **554**, 팔레트 2 **603**,
예외 통 **369**. 팔레트 여덟 모서리 **398 ~ 806**. 적재 격자의 블록 140,
사방 여유 30, 간극 10. 전부 일치한다. 카메라는 화각과 거리에서 지상
분해능을 뽑아 40 mm QR이 몇 픽셀로 찍히는지까지 낸다.

```bash
tools/xacro_expand.sh src/box_cell_description/urdf/box_cell_robot.urdf.xacro -o /tmp/robot.urdf
python3 tools/verify_reach.py /tmp/robot.urdf     # numpy 필요
```

펼친 URDF로 FR5의 FK/IK를 직접 풀어 26개 자세의 도달성을 확인한다.
석션 TCP 오프셋 220.5 mm, 관절 한계, 그리고 **팔꿈치가 상판 아래로 내려가지
않을 것**까지 조건에 넣는다. 마지막 조건이 없으면 IK는 도달한다고 답하지만
실물은 상판을 때린다. `joint_limits.yaml`이 URDF보다 좁게 묶은 관절
(j2, j4, j5)도 함께 지킨다. 안 그러면 이 도구가 통과시킨 자세를 MoveIt이
못 쓰는 일이 생긴다.

```bash
python3 tools/verify_camera_clearance.py /tmp/robot.urdf
```

C1(컨베이어 탑뷰)이 로봇의 동선과 겹치는지 잰다. `verify_reach.py`는 이걸
못 본다. IK는 카메라를 모르기 때문이다. 두 가지를 본다.

- 판독 위치의 x를 훑으며 파지/접근 자세에서 팔과 카메라의 여유
- 판독 이탈점에서 팔레트 상공까지 **이송 경로 전체**의 여유. Pilz PTP는
  관절 공간 직선이라 양 끝이 멀쩡해도 그 사이에서 공구가 뒤로 크게 휜다.

링크를 반지름 60 mm 캡슐로 보는 거친 계산이라 MoveIt(실제 메시 + 패딩)이
언제나 25 mm쯤 더 엄하다. 그만큼 여유를 두고 읽을 것.

```bash
# 시뮬레이터를 먼저 띄운 뒤
python3 tools/verify_place_descent.py
```

돌고 있는 move_group에 직접 물어, 적재 자리 16개와 판독 자리·예외 통에서
**수직 하강 직선이 끝까지 풀리는지** 확인한다. `verify_reach.py`는 "그 점에
갈 수 있는가"만 보는데, 이 셀에서 사이클을 가장 많이 죽인 것은 도달성이
아니라 자세였다. `joint_limits.yaml`의 j2/j4/j5 울타리를 건드렸으면 반드시
이 도구를 다시 돌릴 것. 울타리를 조이면 어느 자리에서는 하강 도중 관절이
한계에 걸려 멈춘다.

현재 상태 : 18개 자리 전부 100%. 해가 전부 같은 자세 계열에 있다
(j4 -88.6 ~ -84.7, j5 +90.0, j2 -110.4 ~ -70.6).

```bash
# 시뮬레이터를 먼저 띄운 뒤 (autostart:=false 로 로봇을 세워 두고)
python3 tools/measure_read_rate.py 30
```

박스 하나를 판독 자리에 세워 두고 판독을 30번 반복해 **성공률·정확도·노출**을
한 번에 낸다. 조명을 손볼 때 이걸로 A/B 한다. 데모를 10분씩 돌려 사이클
로그로 세는 것보다 빠르고, 로봇 동작 실패가 섞이지 않아 원인이 조명인지가
분명하게 갈린다.

성공률만 보면 안 된다. 조명을 낮추면 디코드는 잘 되는데 QR 모서리가 흐려져
위치가 밀릴 수 있고, 흡착 판정은 컵 축에서 30 mm 안을 요구한다. 그래서
정답지(`/sim/boxes`)와 대 본 오차를 함께 낸다.

```bash
python3 tools/make_labels.py                      # qrcode, pillow 필요
```

박스 8개의 QR 라벨 텍스처와 MES 시드 데이터를 만든다. 생성한 라벨을 C1이
실제로 보게 될 크기(97 px)로 줄이고 노이즈를 얹어 디코드해 보면, 8개 전부
코드와 네 모서리가 나온다. 판독 파이프라인이 성립한다는 뜻이다.

## 시나리오

기본은 **infeed**다. `cell.yaml`의 `scenario.mode`가 고른다.

**infeed** — 박스가 컨베이어를 타고 들어온다. 정지 센서에서 서면 C1이 판독하고,
로봇이 흡착으로 집어 팔레트에 **구석부터 하나씩** 쌓는다. 1층 네 자리를
채우고 2층으로 올라간다. 팔레트가 차면 반출한 것으로 보고 비운 뒤 다음
로트를 받는다. 박스를 벨트에 올리는 것은 상류 라인의 일이고 로봇은 관여하지
않는다.

적재 순서는 `cell.yaml`의 격자 공식이 정한다. 슬롯 0이 (col 0, row 0),
즉 팔레트의 한 모서리다.

```
  슬롯 0 → 1 → 2 → 3   1층 (구석에서 시작해 라스터로)
  슬롯 4 → 5 → 6 → 7   2층
```

**circulate** — 기획서 "순환"의 두 팔레트 방식. 팔레트 1이 차면 로봇이
하나씩 꺼내 컨베이어에 되올리고, 판독을 거쳐 팔레트 2에 쌓는다. 2가 차면
방향이 뒤집힌다. 보충 없이 무인 연속 운전을 보이기 위한 구성이다.

실제 셀에서는 상류 컨베이어가 박스를 보내 온다. 시뮬레이터는 그 상류를
만들지 않는다. 대기 박스를 셀 밖 바닥에 세워 두었다가 벨트 입구로 하나씩
올린다. 셀 경계 밖의 일은 셀의 관심사가 아니다.

## 실제로 돌려서 확인한 것

컨테이너를 굽고 두 모드로 띄워 봤다. 결과를 그대로 적는다.

**빌드** — 11개 패키지 전부 통과. rosdep도 "All required rosdeps installed
successfully".

**`hardware:=mock` (Gazebo 없이 MoveIt까지)** — 기획서 R2가 요구하는 모드다.
여기서 확인된 것 :

- `controller_manager`가 `mock_components/GenericSystem`을 물고 두 컨트롤러
  활성화

- `scene_publisher`가 반출에 맞춰 `stacked_p1_s7` … 를 순서대로 제거

### 실측 4 : 전체 사이클을 끝까지 돌리기

여기까지가 "박스를 집었다"였다. **팔레트에 실제로 쌓기까지** 네 가지를 더
고쳐야 했다. 넷 다 증상은 "계획 실패"인데 원인은 전혀 다른 곳이었다.

**(1) 영상 지연 — 판독 위치가 138 mm 틀렸다.**
`label_reader`가 마지막으로 도착한 프레임을 쓰고 있었다. 렌더 → 브리지 →
구독 파이프라인에 그림이 고여 있어서, 실측 지연이 0.2 ~ 1.4초였다.
벨트가 0.25 m/s이니 그 사이 박스는 138 mm를 간다. 박스가 x=440에 서 있는데
판독은 x=302를 내놓았고, 로봇은 아무것도 없는 자리로 내려갔다.

실물 산업용 카메라처럼 **트리거 이후에 찍힌 프레임만** 쓰게 고쳤다.
헤더 시각이 트리거 시각보다 새로운 프레임을 기다린다. 벨트가 선 뒤
0.6초를 정착에 쓴 다음 찍는다. 고친 뒤 판독 오차는 정답지 대비 **2 mm**.

**(2) C1 카메라가 로봇 하강 통로에 있었다.**
광축 기울기가 20도일 때 카메라는 x=277, 팔이 지나는 평면은 x=405로
128 mm밖에 안 떨어져 있었다. MoveIt이 `forearm_link` / `wrist1_link` /
`wrist2_link`와 `camera_c1_conveyor`의 접촉을 잡아 계획을 버렸다.
기울기를 40도로 키워 카메라를 x=164로 보냈다. 표적까지 거리는 375로
그대로라 지상 분해능은 유지된다.

    tools/verify_camera_clearance.py 실측 (접근 자세 여유)
      20도  x=400에서 +25 mm,  이송 경로 -9 mm   -> 막힌다
      30도  x=400에서 +72 mm,  이송 경로 -9 mm   -> 이송이 막힌다
      40도  x=400에서 +124 mm, 이송 경로 +38 mm  -> 통과

**(3) 슬롯 간극 10 mm로는 이웃이 둘인 자리에 못 놓는다.**
내려놓을 박스도 이웃 박스도 모두 충돌체이고 각각 패딩이 붙는다. 10 mm가
남지 않아 MoveIt이 직선 하강을 61 ~ 79%까지만 풀고 포기했다. 피치를
70에서 75로(간극 15) 넓혔다. 색칠 구역 200 각 안에 그대로 들어간다.

**(4) 가장 오래 걸린 것 — 로봇이 같은 자리에 다른 자세로 갔다.**
증상은 `직선 경로가 43%만 풀렸다`였다. 적재 상공에 TCP가 목표와 0.4 mm
차이로 정확히 서 있는데, 거기서 바로 아래로 내리는 직선이 안 풀렸다.
같은 지점을 IK로 풀어 그 자세에서 시작하면 100% 풀렸다. 자세가 문제였다.

FR5는 같은 TCP 지점에 여러 관절 자세로 갈 수 있다. 예외 통 투하 지점에
도착한 두 자세를 실제로 잡았다.

    j1=+16.9  j2=  -7.5  j3=-77.4  j4=-185.2  j5=+90.0  j6=-73.1
    j1=-131.0 j2=-172.6  j3=+77.4  j4=  +5.2  j5=-90.0  j6=-41.0

TCP는 같은 점인데 j1이 148도 다르다. 그리고 이 자세들은 등가가 아니다.
18개 목표(팔레트 2장 × 4자리 × 2층, 판독 자리, 예외 통)마다 무작위 시드로
IK를 여러 번 풀어 하강이 100% 풀리는 해만 모아 보니, 가려 주는 것은
**j2와 j4와 j5**뿐이었다.

    성공 해   j2 -110.6 ~ -69.3    j4 -95.4 ~ -84.5    j5 +90
    실패 해   j2 -180.2/-136.7/-15.2   j4 -170.9/+75.7/-225.4   j5 -90

그래서 `joint_limits.yaml`에서 j2, j4, j5의 각도 범위를 묶었다. 실물
팔레타이저도 이렇게 쓴다. 로봇을 한 자세 계열에 묶어 두어야 같은 자리에
늘 같은 모양으로 가고, 사이클마다 궤적이 달라지지 않는다.

대기 자세도 옮겼다. 전에는 `[0, -90, +90, -90, -90, 0]`으로 j5가 -90,
즉 작동 계열의 거울상이었다. 계획기는 IK를 현재 자세에서 시드해 풀므로
대기 자세가 거울상이면 팔이 자꾸 그쪽으로 끌려간다. 지금은
`[0, -90, -90, -90, +90, 0]`이다.

실패 처리도 고쳤다. 전에는 손만 비우고 팔은 그 자리에 두었다. 그러면
다음 사이클이 검증되지 않은 자세에서 시작해 계속 무너진다. 이제
**대기 자세로 복귀한 다음** 끝낸다.

**결과** (헤드리스, GPU, 실시간 계수 1.00) :

- 팔레트 1의 1층 네 자리를 **구석부터** 채우고 2층 구석까지

      층0  box_4 (0.916, 0.245)   목표 (0.9125, 0.2475)   오차 4 mm

- 판독에 실패한 박스 3개는 예외 통으로 갔다 (설계대로다)

### 실측 5 : 판독 조명과 헛집기

**조명이 판독 구간을 태우고 있었다.**
`tools/measure_read_rate.py`로 재 보니 판독 구간 평균 밝기 203, 포화 화소
30%였다. 화면의 3분의 1이 255에 붙어 있으면 QR의 검은 모듈과 흰 모듈
경계가 뭉갠다.

원인은 감쇠 계수였다. spot의 감쇠는 `1/(constant + linear*d + quadratic*d²)`
인데 `constant`가 0.4면 거리 0.4 m에서 배율이 **2.05**가 된다. 조명이 제
세기보다 두 배로 밝아지는 셈이라 물리적으로 말이 안 된다. 1.0으로 고치고
세기도 낮췄다. 실물 카메라는 자동 노출이 있어 이런 조명이어도 알아서
조이지만, gz 카메라는 없어서 조명 쪽에서 맞춰 줘야 한다.

    조명           판독 성공률      판독 구간 평균   포화
    원래           26~28/30 (87~93%)      203        30%
    감쇠 정정       30/30 (100%)          185        23%
    세기까지 낮춤    28~30/30 (93~100%)    169        16%

위치 정확도는 나빠지지 않았다 (x 4.8 mm, y 2.1 mm. 흡착 여유 30 mm).
노출 관련 수치는 전부 `cell.yaml`의 `lighting:` 블록으로 옮겼다. 전에는
월드 SDF에 박혀 있었다.

**헛집기를 아무도 몰랐다.**
ES45는 잡았는지 되물을 수 없다. 그래서 "동작을 끝냈다"와 "옮겼다"가 다른
이야기인데, 그걸 확인하는 곳이 없었다. 한 실행에서 흡착이 헛나가 박스가
벨트에 그대로 남았는데 사이클은 성공으로 기록됐고, 다음 사이클이 같은
박스를 다시 읽어 헛집기를 여섯 번 반복하며 **팔레트를 유령으로 채웠다.**
로그만 보면 8사이클 완료였고 실제로 옮겨진 박스는 두 개였다.

확인에 새 장비는 필요 없다. 정지 센서(광전 센서)는 이미 있고, 집어 갔으면
그 자리가 비어야 한다. 실물 팔레타이저의 표준 인터록이다. 집은 뒤에도
센서가 그 박스를 보고 있으면 적재 기록을 남기지 않고 다시 시도한다.

흡착이 왜 실패했는지도 남긴다. 조건을 못 맞춘 후보 중 가장 가까웠던 것의
축방향 거리 · 옆거리 · 기울기를 찍어 무엇이 모자랐는지 바로 보이게 했다.

**결과** — 박스 8개가 전부 팔레트에 올라갔다. 한 판을 다 채웠다.

    사이클 1~8 연속 완료, 37~43초

### 실측 6 : 헛집기의 진짜 원인은 롤러 피치였다

`흡착 조건을 만족하는 박스가 없다`가 반복됐다. 판독 위치 오차는 2 mm이고
하강 직선도 100% 풀리는데 컵이 박스를 못 물었다. 흡착 판정에 왜 떨어졌는지
찍게 해 보니 답이 한 줄로 나왔다.

    흡착 조건 미달. 가장 가까운 box_3 : 기울기 28.2 도 (허용 20)

박스의 실제 자세를 보니 쿼터니언이 (0, -0.245, 0, 0.970), y축 28.4도였다.
**박스가 롤러 위에 비스듬히 얹혀 있었다.**

원인은 롤러 피치다. 60 각 박스에 피치 55면 박스가 롤러 한두 개에만 얹힌다.
그 상태로 멈추면 골에 빠져 기운다. cell.yaml에는 "박스 60 각이 사이로
빠지지 않는 간격"이라고 적혀 있었는데, 빠지지 않는 것과 반듯이 서는 것은
다른 이야기였다.

실물 롤러 컨베이어의 기본 규칙은 **화물이 언제나 롤러 3개 이상에 얹힐 것**
이다. 60 각이면 피치가 20 이하여야 한다. 작은 화물을 다루는 라인이 가는
롤러를 촘촘히 쓰는 이유가 이것이다.

전 구간을 피치 20으로 깔아 보니 기울기는 **28.4도에서 0.0도**가 됐는데,
롤러가 83개로 늘어 실시간 계수가 1.00에서 **0.16**으로 주저앉았다.
원인을 좁혀 보니 :

    플러그인 83개를 1개로 합침    -> 0.16  (변화 없음)
    롤러 질량 0.05 -> 0.20        -> 0.17  (변화 없음)

링크와 접촉의 개수 자체가 비용이었다. 그래서 두 구간으로 나눴다.

    정밀 구간  x 40~500   지름 18 / 피치 20   24개   박스가 서고 로봇이 집는 곳
    이송 구간  나머지     지름 50 / 피치 55   11개   지나가기만 하는 곳

    롤러 35개, 실시간 계수 **1.04**, 판독 자리 기울기 **0.0도**

굵기가 다르면 같은 벨트 속도를 내는 각속도가 다르므로(표면 속도 = ω × r),
구동 토픽도 구간별로 나눴다. 하나로 보내면 굵은 롤러가 빨라져 박스를 끈다.

### 실측 7 : QR 여백이 규격 미달이었다

판독이 간헐적으로 실패하는 문제를 조명 탓으로 보고 낮췄더니 성공률이
87~93%에서 93~100%로 올랐다. 그런데 데모에서는 여전히 8개 중 2개가 3회를
다 실패해 예외 통으로 갔다. 실패한 프레임을 받아 보니 조명이 아니었다.

**QR 둘레의 흰 여백(quiet zone)이 규격 미달이었다.** QR 규격은 사방 4모듈을
요구한다. 라벨 50에서 문자열 폭 4를 빼면 QR이 41이고 version 1은 21모듈이니
모듈이 1.95다. 그런데 여백이 2.5, 즉 **1.3모듈**이었다. 규격의 3분의 1이다.
디코더가 찾기 패턴의 경계를 잡을 때도 있고 못 잡을 때도 있었다.

    라벨 54 - 여백 7.5x2 - 문자열 3.5 = QR 35.5, 모듈 1.69
    여백 7.5 / 1.69 = 4.4 모듈  -> 규격 통과

실은 이 수정이 한동안 **그림에 반영되지 않고 있었다.** 라벨 텍스처는
`tools/make_labels.py`가 만드는데, entrypoint가 "파일이 없으면 만든다"로
되어 있어 이미 있는 이틀 전 PNG가 계속 쓰였다. cell.yaml의 치수를 고친
사람은 바뀌었다고 믿는데 렌더링되는 그림은 그대로인, 제일 나쁜 종류의
어긋남이다. 라벨 평면 메시(label_plane.obj)도 같은 스크립트가 만들므로
함께 어긋난다. 지금은 이미지 빌드가 반드시 다시 만들고, entrypoint도
cell.yaml이 더 새로우면 다시 만든다.

제대로 반영한 뒤 다시 재니 이렇다.

    판독 성공률   40/40 (100%)
    위치 정확도   x 1.5 mm, y 1.8 mm   (여백 고치기 전 4.3 / 2.1)

여백은 디코드 성공률만이 아니라 **모서리 좌표 정확도**도 좌우한다.
찾기 패턴의 경계를 정확히 잡아야 네 모서리가 제자리에 나온다.

### 실측 8 : C4 근접 재시도가 근접하지 않았다

기획서 5.4는 판독 3회째에 C4 손목 카메라로 근접 재시도하라고 한다.
구현은 C4 셔터만 누르고 있었다. 그때 팔은 팔레트 위 대기 자세라 컨베이어가
화각에 아예 없었다. **3회째는 언제나 실패였고, 사실상 재시도가 두 번뿐이었다.**

이제 손목을 판독 자리 위로 옮긴 다음 찍는다. C4는 TCP 전방 150에서 광축이
모이므로, TCP를 박스 상면 위 150에 세우면 라벨이 화각 한가운데에 온다.
찍은 뒤에는 반드시 대기 자세로 돌아온다. 안 그러면 다음 동작이 검증하지
않은 자세에서 시작한다.

### 실측 : 실시간 계수를 0.004에서 1.00으로

세 단계를 밟았고, 각 단계가 무엇을 고쳤는지 수치로 남는다.

| 상태 | 실시간 계수 | GPU |
|---|---|---|
| 처음 (소프트웨어 EGL, 카메라 4대 30 Hz) | 0.004 | 0 % |
| NVIDIA EGL ICD 주입 후 | 0.016 | 21 % |
| 카메라 갱신률을 실제 쓰임에 맞춘 뒤 | **1.00** | 43 % |

**첫 번째 : NVIDIA EGL ICD가 없었다.** `nvidia-container-toolkit`은 드라이버
라이브러리(`libEGL_nvidia.so`)는 컨테이너에 넣어 주는데 등록 파일
`/usr/share/glvnd/egl_vendor.d/10_nvidia.json`은 넣어 주지 않았다. libglvnd가
mesa만 발견해 소프트웨어 EGL로 떨어졌다. 이미지에 그 파일을 직접 넣어 해결했다.

**두 번째 : 카메라가 병목이었다.** 물리가 아니었다. 카메라를 1 Hz로 낮췄더니
실시간 계수가 즉시 1.00이 나왔다. 넷을 30 Hz로 돌리면 프레임 복사만으로
CPU가 포화된다. 그래서 `cell.yaml`에 `stream:` 블록을 두어 시뮬레이터가
실제로 렌더링할 것을 따로 정한다. `realsense.yaml`의 30 Hz는 하드웨어
제원이라 그대로 둔다.

낮춰도 되는 근거는 기획서 5.4에 있다. "판독은 C1 한 대로 완결하고 나머지는
확인과 기록을 맡는다." C1은 10 Hz에 깊이를 끄고(판독에 깊이를 쓰지 않는다),
C2/C3는 5 Hz, C4는 10 Hz다.

### 실측 2 : GPU를 실제로 쓰게 만들기 (창 모드)

헤드리스에서 1.00이 나온 뒤에도 **창 모드(GUI)에서는 GPU 사용률이 0 %**였다.
컨테이너 안에서 `glxinfo`를 보니 `llvmpipe`였다.

원인은 호스트가 **Wayland 세션**이라는 것이다. 컨테이너의 GLX는 Xwayland를
거치는데, 그때 libglvnd가 벤더를 자동으로 못 고르고 mesa로 떨어진다.
`libGLX_nvidia.so`는 멀쩡히 주입돼 있는데도 그렇다.

`__GLX_VENDOR_LIBRARY_NAME=nvidia` 하나로 해결된다. Dockerfile의 ENV에
넣어 두었으므로 따로 줄 것은 없다.

| 경로 | 무엇이 필요한가 |
|---|---|
| EGL (헤드리스 센서 렌더링) | `/usr/share/glvnd/egl_vendor.d/10_nvidia.json` |
| GLX (창 모드 GUI) | `__GLX_VENDOR_LIBRARY_NAME=nvidia` |

둘 다 이미지에 들어 있다. 확인하려면 :

```bash
./docker/run.sh bash -lc 'glxinfo -B | grep "OpenGL renderer"'
```

`NVIDIA GeForce RTX 4090`이 나와야 한다. `llvmpipe`가 나오면 GPU를 안 쓰는 것이다.

### 실측 3 : 로봇이 덜덜 떠는 문제

`gz_ros2_control`의 위치 제어식은 이것이다.

```
target_vel = gain * update_rate * (목표 - 현재)
```

**update_rate가 이미 곱해져 있다.** 그래서 `position_proportional_gain`은
"한 제어 주기에 남은 오차의 몇 배를 없앨 것인가"라는 뜻이고, 1.0이
데드비트(한 주기에 정확히 0으로)다. 이걸 모르고 50을 넣으면 실효 이득이
5000이 되어 0.0006 rad만 벌어져도 속도 명령이 관절 한계에 붙는다.

정지 상태에서 잰 값이다.

| gain | 위치 진폭(p-p) | 속도 rms | 속도 최대 |
|---|---|---|---|
| 50 | 0.14 ~ 0.31 rad (8~18°) | 1.6 ~ 3.1 rad/s | **관절 한계에 포화** |
| **0.9** | **0.00000 rad** | **0.0000** | **0.000** |

0.1(기본값)은 반대로 너무 느려서 정상 오차가 v/10이 된다. 이송 속도
1.1 rad/s에서 0.11 rad이라 `trajectory` 허용치 0.10을 그냥 넘기고,
`PATH_TOLERANCE_VIOLATED`로 실행이 중단된다.

## 실행에 필요한 것

이 PC는 Ubuntu 26.04라 ROS 2 Jazzy 공식 바이너리가 없다(Jazzy는 24.04용이다).
그래서 시뮬레이션은 컨테이너로 돈다. 기획서 4절이 엣지를 Docker로 배포한다고
정해 둔 것과 같은 방식이다.

Docker는 설치 완료. **남은 것은 NVIDIA 컨테이너 런타임 하나뿐이고, 위에서
적었듯 이건 선택이 아니다.** Ubuntu 기본 저장소에는 없어서 NVIDIA 저장소를
추가해야 한다.

```bash
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
```

```bash
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list
```

```bash
sudo apt update && sudo apt install -y nvidia-container-toolkit && sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker
```

그다음 :

```bash
./docker/build.sh      # 이미 한 번 성공했다. 소스만 바뀌면 1분.
./docker/run.sh        # 전체 데모
```

`docker/run.sh`가 NVIDIA 런타임을 자동으로 감지해 `--gpus all`을 붙인다.
없으면 경고를 내고 소프트웨어 렌더링으로 떨어진다.

## 실행

```bash
./docker/run.sh                                    # Gazebo + MoveIt + 전체 로직
./docker/run.sh ros2 launch box_cell_bringup demo.launch.py hardware:=mock
./docker/run.sh ros2 launch box_cell_bringup demo.launch.py rviz:=true
./docker/run.sh ros2 launch box_cell_bringup demo.launch.py autostart:=false
```

`hardware:=mock`은 Gazebo 없이 `mock_components/GenericSystem`으로 돈다.
기획서 R2의 "실물 없이 MoveIt2까지 전부 구동"이 이것이다. 궤적은 제대로
계산되고 실행만 흉내다. 노트북에서 로직을 고칠 때 쓴다.

`autostart:=false`면 상태 기계가 IDLE에서 기다린다. 시작 순간을 사람이
잡고 싶을 때 :

```bash
ros2 topic pub --once /cell/command std_msgs/msg/String "{data: start}"
```

MES 대시보드는 <http://localhost:8020>.

| `box_cell_logic` | `task_manager`(상태 기계), `pallet_manager`(적재 기록), `mes_client` |
| `box_cell_conveyor` | `conveyor_driver`. 벨트 구동과 정지 센서 |
| `box_cell_mes` | FastAPI + SQLite MES 서버, 대시보드 |
| `box_cell_bringup` | 런치와 파라미터 |

### cell.yaml 하나만 고치면 된다

상판 1200×800×H750, 로봇 중심 (405, 311), 컨베이어 800×150(벨트 상면 상판
위 180), 팔레트 300각 두 장 (950, 210)과 (950, 570), 예외 통 (95, 110),
박스 60×60×40 여덟 개. 이 숫자들은 `cell.yaml` 한 곳에만 있다.

- URDF(xacro)가 `xacro.load_yaml`로 읽는다
- 노드들이 `cell_geometry.py`로 읽는다
- 검증 도구가 같은 파일로 기획서 수치를 재현한다

치수를 노드에 다시 적으면 언젠가 반드시 어긋나고, 어긋난 줄도 모른 채
데모 당일에 알게 된다.

## 실물을 얼마나 따라갔나

의도적으로 실물 그대로 둔 것들이다. 편하게 만들면 시뮬레이터에서만 되는
데모가 되기 때문이다.

**석션에 센서가 없다.** ES45는 24 V I/O 장치다. 통신도 센서도 없고, 잡았는지
되물을 방법이 없다. 그래서 `/gripper/vacuum`의 응답은 "명령을 냈다"는 뜻이지
"잡았다"는 뜻이 아니다. 상위 로직은 진공을 켜고 정해진 시간을 기다리는 것
말고 할 수 있는 게 없다. `gripper_driver`는 흡착 대상을 고를 때도 실물의
흡착 조건(컵에서 상면까지 거리, 축 정렬 각도)을 그대로 판정하고, 못 맞추면
아무것도 붙지 않는다. 실물에서 헛집는 것과 같다.

**컨베이어가 물리로 움직인다.** Gazebo에는 벨트 표면 속도를 흉내 내는 시스템이
없다. 박스를 텔레포트로 옮기면 간단하지만, 그 물체는 속도도 접촉도 거짓이라
석션이 잡는 순간이 실물과 달라진다. 대신 `conveyor_driver`가 박스 속도를 읽고
마찰 보상 + 속도 오차 비례로 힘을 실어 벨트 속도를 따라가게 한다.

**컨트롤러가 100 Hz다.** 실물 FR5 컨트롤러의 관절 갱신 주기에 맞췄다.
시뮬레이터만 250 Hz로 돌리면 실물에서 재현되지 않는 매끄러움이 나온다.

**MoveIt은 Planning Scene에 등록된 것만 안다.** 상판(받침 개구 400각을 피해
네 조각), 컨베이어, 팔레트 2장, 예외 통, 그리고 **카메라 갠트리 기둥 두 개**를
등록한다. 기둥이 로봇 도달 고리(외경 884) 안에 있어서 이건 선택이 아니다.
적재된 박스는 시뮬레이터의 정답지가 아니라 `pallet_manager`의 **적재 기록**을
보고 만든다. 실물에는 정답지가 없고 기록만 있기 때문이다.

**판독 실패가 정상 동작의 일부다.** 3회까지 재시도하고, 3회째는 C4 손목
카메라로 근접 재시도한다. 그래도 안 되면 예외 통으로 보낸다.

**MES가 죽어도 로봇이 서지 않는다.** `mes_client`가 로컬 큐에 쌓았다가
재전송한다. `event_id`가 멱등키라 중복 기록이 생기지 않는다.

### 시뮬레이터만의 사정

`/sim/boxes`는 정답지다. 실물에는 없다. 읽어도 되는 곳은 셋뿐이고 코드에
그렇게 적어 두었다 — `conveyor_driver`(힘을 실을 대상), `gripper_driver`
(석션이 붙일 대상), Dry Run 채점. 판독과 적재 로직은 이것을 보지 않는다.

## 아직 안 된 것

정직하게 적는다.

- **컨베이어가 서 있는 박스를 못 민다. 아직 안 풀렸다.**

  이번에 이송 기구를 **구동 롤러 컨베이어**로 바꿨다. 롤러 31개(반지름 25,
  피치 55)를 `conveyor.urdf.xacro`의 별도 모델로 두고, gz의 JointController가
  속도 명령 하나로 전부 돌린다(각속도 = 벨트 속도 / 반지름 = 10 rad/s).
  힘도 자세도 명령하지 않는다. 로봇 관절이 도는 것과 같은 경로다.

  하드웨어 쪽은 확인됐다. 모델이 스폰되고, 롤러가 실제로 돌고(자세가 계속
  바뀐다), 회전 방향도 바로잡았고(처음엔 축 부호가 반대라 박스가 상류로
  밀렸다), 기어박스와 받침 다리 윗면도 롤러면 아래로 내렸다. 박스는 롤러
  위 정확한 높이(z=0.950)에 내려앉는다. 접촉은 있다.

  그런데 **박스가 안 실린다.** 롤러는 돌고, 박스는 그 위에 닿아 있고,
  마찰은 0.9인데 움직이지 않는다.

  두 관측을 함께 놓으면 물체가 물리적으로 얼어 있다고 볼 수밖에 없다.
  위로 50 N(무게 3.4 N)을 걸어도 안 뜨고, 도는 롤러 위에서도 안 끌린다.
  중력으로 떨어지기는 한다. gz가 안착한 물체를 재우고, 접촉 상대가 나중에
  움직이기 시작해도 다시 깨우지 않는 것으로 보인다.
  `<allow_auto_disable>false</allow_auto_disable>`도 듣지 않았다.

  **다음 수**는 박스를 미리 놓아 두지 않는 것이다. 롤러가 이미 도는 상태에서
  필요한 순간에 하나씩 `create`로 만들면, 움직이는 롤러 위에 내려앉아 곧바로
  실려 간다. 잠들 틈이 없다. `create`는 정상 동작하는 유일한 엔티티 조작이고,
  사이클당 한 번이면 되므로 부담도 없다.

  (아래는 이 문제를 좁혀 온 기록이다.)
  물리 엔진이 정지한 물체를 재우는데, **잠든 물체는 ApplyLinkWrench로 건 힘을
  받지 않는다.** 실측으로 확인했다 : 벨트에 서 있는 박스는 50 N에도 꿈쩍
  않는데, 같은 20 N을 공중에서 떨어지는(=깨어 있는) 박스에 걸면 1.4 m를
  날아간다. `set_pose`와 `remove`가 `data: true`만 돌려주고 아무 일도 하지
  않던 것도 같은 뿌리로 보인다.

  SDF의 `<allow_auto_disable>false</allow_auto_disable>`은 듣지 않았다.
  gz-sim의 DART 구현이 그 항목을 보지 않는 것 같다.

  다음 수는 **벨트를 실제로 움직이는 몸체로 만드는 것**이다. 벨트를 프리즘
  조인트 위의 얇은 링크로 두고 속도 명령으로 굴리면, 박스는 마찰로 실려 간다.
  접촉은 잠든 물체를 깨우므로 이 문제가 아예 생기지 않고, 실물 컨베이어와
  가장 가까운 모형이기도 하다. 끝까지 간 벨트 링크는 제자리로 되돌린다.

- **박스가 실제로 팔레트에 쌓이는 것을 아직 못 봤다.** 아홉 구간이 전부
  완주하고(18~21초, 목표 20초) 컨트롤러 중단도 0회지만, 박스가 옮겨지지
  않는다. 원인이 두 겹이다.

  하나는 고쳤다. 흡착의 `DetachableJoint`가 `parent_link`을 못 찾아 조용히
  죽어 있었다. URDF를 SDF로 바꿀 때 고정 조인트로만 붙은 링크(es45_cup 등)가
  wrist3_link에 병합되기 때문이다. `wrist3_link`로 바꿔 해결했다.

  나머지 하나가 남았다. **`/world/box_cell/set_pose`와 `/remove`가
  `data: true`를 돌려주면서 아무 일도 하지 않는다.** `create`는 정상이다.
  피더가 박스를 벨트 입구로 옮기는 데 set_pose를 쓰고 있어서, 8개를 전부
  "투입했다"고 기록하고는 실제로는 하나도 안 옮긴다. 대기 큐만 비어
  "투입할 박스가 없다 → 팔레트 반출"이 무한히 도는 교착에 빠진다.

  다음 수는 자세 이동을 버리는 것이다. 상류 인피드 구간을 벨트에 붙여
  기동 때 박스를 그 위에 create로 만들어 두고, 컨베이어가 하나씩 밀어
  넣게 한다. gz 엔티티를 실행 중에 조작할 일이 없어진다.
- ~~적재 결과 확인이 없다.~~ **`stack_check`가 한다.** C2 깊이로 놓은
  자리의 높이를 재어 기대와 맞는지 본다. `task_manager`가 RECORD 직전에
  부르고, 안 보이면 기록하지 않고 셀을 세운다. 실측 덮임 89~100%,
  높이 오차 1 mm 안. 깊이가 안 오면 **보류**이지 통과가 아니다.
- **Pilz PTP가 종종 충돌 경로를 낸다.** ValidateSolution이 걸러 내고 OMPL이
  받아 주므로 동작에는 지장이 없지만, 계획 시간이 낭비된다. 고정 웨이포인트를
  더 촘촘히 잡으면 줄어들 여지가 있다.
- **갠트리 기둥 위치는 잠정값이다.** 기획서 7절에서 "발주 도면에서 확정"으로
  남아 있다. `cell.yaml`의 `gantry:` 블록에 `tbd: true`로 표시해 두었고,
  도면이 나오면 그 블록만 고치면 형상과 Planning Scene이 함께 따라온다.
- **C3 기종 미정.** 위에 적은 대로 `model` 한 줄이다.
- ~~트윈 브리지가 없다.~~ **`twin_bridge`가 있다.** 기획서 D4.
  셀 상태를 JSON 한 덩어리로 파일(`/tmp/box_cell/twin.json`),
  토픽(`/twin/state`), HTTP(`:8030/twin`) 세 곳에 낸다. 내기만 하고 받지
  않는다. 스키마가 시뮬/실물에 의존하지 않아 실물 셀에서 `source:=real`로
  그대로 띄운다.
- ~~Dry Run 채점기가 없다.~~ **`dry_run_scorer`가 있다.** 기획서 D3.
  처리량, 사이클 시간(투입/순환을 갈라서), 판독 성공률과 신뢰도, 예외 사유,
  적재 정확도(기록 대 정답지)를 `/tmp/box_cell/dry_run.json`에 쓴다.
- **순환 사이클이 목표의 두 배다(38~41초).** 픽앤플레이스가 두 번이라

- **비상정지는 모양뿐이다.** 배선이 없다. 실물에서는 ROS를 거치지 않고
  컨트롤러 안전 입력에 직결해야 한다. `docs/real_robot_bringup.md` 참고.

## 실행에 필요한 것 (헤드리스에서 알아낸 것)

- `--shm-size=2g`. 기본 64 MB로는 Gazebo가 죽는다.
- `-e __EGL_VENDOR_LIBRARY_FILENAMES=/usr/share/glvnd/egl_vendor.d/10_nvidia.json`.
  이게 없으면 헤드리스 EGL이 소프트웨어 렌더러를 잡아 GPU 사용률이 0이 되고
  카메라가 초당 한 장도 못 낸다.
- 소켓 버퍼(`net.core.rmem_max`)가 4 MB인 호스트에서 1920x1080 컬러 원본
  (6.2 MB)은 **한 장이 버퍼보다 커서** 대부분 유실된다. 그래서 판독기는
  압축 토픽(`.../image/compressed`)을 받는다. 해상도는 실기 제원 그대로 둔다.
